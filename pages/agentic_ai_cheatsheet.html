1. Syllabus map and high-yield vocabulary

An agent is a system that perceives an environment and selects actions to achieve objectives. Agentic AI emphasizes goal-directed, partially autonomous operation: the system can plan, use tools, observe results, revise its approach, and stop when a success condition is met. LLMs are often the reasoning and language interface, but the agent is the complete system around the model.

PERCEIVEInput and state

Collect user intent, environment signals, documents, tool results, and prior context.

REASONDecision policy

Interpret, decompose, plan, select tools, verify, and decide whether to continue.

ACTEnvironment change

Answer, call an API, query a store, write a file, or delegate to another agent.

Exam distinction: A chatbot usually responds to a turn. An agent maintains an objective and can execute a multi-step policy. An LLM is a model; an agent is an engineered runtime that may use an LLM, memory, tools, control logic, and guardrails.

3. Intelligent agents: architecture, components, lifecycle

An intelligent agent maps percept history to actions. A useful engineering abstraction is:

Agent = Goal / task specification + state + policy / planner + tools + memory + verifier + runtime controls
Core components. The environment exposes observations and action affordances. The model or policy selects the next step. A planner decomposes the task. Tools provide capabilities unavailable in the model. State tracks current progress. Memory persists useful information. A verifier checks evidence, constraints, and completion. Guardrails enforce safety, permissions, budgets, and schemas.
Agent lifecycle. Specify objective and success criteria → initialize context, identity, tools, and memory → plan subtasks → execute actions → observe outputs → reflect / verify → update state and memory → terminate, escalate, or recover → evaluate traces and outcomes.
Design rule: Every loop needs a termination condition, maximum steps or budget, error policy, and human-escalation path. Otherwise, autonomy becomes uncontrolled iteration.

Remember: Autonomy is not intelligence. It is the degree of independent decision-making and action permitted by the system design.

5. Agent design principles and task decomposition

1. Start with the objective. Define input, output, constraints, success metric, failure modes, and who may approve irreversible actions.
2. Decompose by dependency. Split a task into subtasks with clear inputs/outputs; use parallel branches only when subtasks are independent.
3. Make state explicit. Store plan, completed steps, evidence, pending decisions, tool results, and retry count as structured state.
4. Prefer least privilege. Give each tool the smallest permission and narrowest argument schema required.
5. Separate propose from commit. A model may draft an action; a policy layer should validate and authorize execution.
6. Design for recovery. Use retries with backoff, alternate tools, compensation actions, checkpointing, and human escalation.

Decomposition patterns

6. ReAct framework: Reasoning + Acting

ReAct interleaves reasoning traces and task-specific actions. The reasoning helps the system form, track, and update a plan; actions query an external environment and return observations. The original paper reports improved performance and interpretability over approaches that separate reasoning and acting.[1]

Question: What is the status of order O-17?
Thought: I need authoritative order data.
Action: get_order_status({"order_id":"O-17"})
Observation: {"status":"shipped", "eta":"2026-09-04"}
Thought: The result is sufficient; compose a concise answer.
Final: Order O-17 has shipped; estimated delivery is 4 Sep 2026.
Practical note: In production, do not expose private chain-of-thought. Log concise rationales, tool calls, observations, and verification results instead. ReAct is a control pattern, not a guarantee of correctness.

7. Fundamentals of multi-agent systems (MAS)

A multi-agent system contains multiple semi-autonomous agents that interact in a shared or connected environment. Agents may cooperate, compete, negotiate, communicate, or coordinate through a supervisor. The main engineering question is not “how many agents?” but “what separation of responsibility improves the objective?”

Coordination modelIdeaTrade-off
Centralized supervisorOne coordinator assigns tasks and integrates results.Simple governance, but a bottleneck and single point of failure.
Peer-to-peerAgents communicate directly and self-organize.Flexible, but harder to debug and control.
Blackboard / shared stateAgents read and write a common workspace.Good for asynchronous collaboration; needs concurrency control.
Market / negotiationAgents bid, negotiate, or select resources.Useful for allocation; adds protocol and incentive complexity.
MAS exam points: define roles and capabilities; specify message formats; maintain shared task state; prevent circular delegation; handle conflicts; authenticate agents; cap cost and latency; and evaluate both individual and collective performance.

Software engineering

Customer operations

Research and knowledge work

Search sources, extract evidence, compare claims, synthesize reports, and cite provenance.

Business process automation

Coordinate email, forms, databases, calendars, approvals, and enterprise APIs.

Robotics and IoT

Perceive sensors, plan actions, control devices, and recover from environmental changes.

Personalized tutoring, formative feedback, question generation, and learning-path planning.

High-impact caution: In health, finance, employment, legal, safety, or identity workflows, autonomy must be bounded by domain controls, auditability, privacy protection, and meaningful human review.

10. Large Language Models and Agent Development

LLM essentials

An LLM is a neural sequence model trained on large text corpora to predict tokens. Transformer attention allows each token representation to use information from other positions. Pretraining gives broad statistical and linguistic competence; instruction tuning and preference optimization improve following of natural-language tasks. An LLM alone produces text. Agent engineering adds the environment interface, tools, state, memory, control flow, and verification.

LLM role in an agentExample
InterpreterConvert user intent into a structured task.
PlannerGenerate subtasks, dependencies, and next actions.
RouterSelect a specialist, retriever, or tool.
GeneratorWrite an answer, code, or artifact.
Critic / verifierCheck constraints, evidence, schema, and quality.

Structured prompt template
ROLE: You are a verification agent.
OBJECTIVE: Answer the question using only supplied evidence.
INPUT: {question}
TOOLS: search(query), calculator(expression)
POLICY: Cite evidence; never invent missing facts; ask for approval before writes.
PROCESS: plan → retrieve → compare → verify → answer.
OUTPUT JSON SCHEMA: {answer, evidence_ids[], confidence, needs_human_review}
Prompt engineering formula: Role + objective + context + constraints + tools + procedure + output schema + failure behavior + examples.

12. Tool integration and function calling

Function calling gives a model a formal interface for proposing an action with named arguments. The runtime, not the model, executes the function, validates arguments, applies permissions, and returns the tool result. The Hugging Face Agents course describes the typical loop as Think → Act → Observe and shows action/tool-result messages in the conversation.[4]

Tool contract. Name, purpose, JSON schema, required and optional fields, units, error format, latency, side effects, authentication, and permissions.
Safety controls. Validate types and ranges; sanitize inputs; use allowlists; isolate code execution; redact secrets; rate-limit; log call ID and result; require confirmation for irreversible effects.
tool = {
  "name": "get_weather",
  "description": "Read current weather for a city",
  "parameters": {"type":"object", "properties":{"city":{"type":"string"}}, "required":["city"]}
}
# runtime: validate → authorize → execute → return observation

Framework selection heuristic: Choose a chain for a stable path, a graph for explicit control and state, a role/crew model for organizational decomposition, a conversation model for agent interaction, and a lightweight code agent for minimal abstraction.

14. Development of a simple LLM-based agent

def run_agent(user_goal, tools, max_steps=8):
    state = {"goal": user_goal, "history": [], "steps": 0}
    while state["steps"] < max_steps:
        prompt = build_prompt(state, tool_schemas(tools))
        decision = llm_json(prompt, schema={
            "type":"object",
            "properties": {
                "kind":{"enum":["tool_call","final","ask_human"]},
                "tool":{"type":"string"},
                "args":{"type":"object"},
                "answer":{"type":"string"}
            }, "required":["kind"]})
        if decision["kind"] == "final":
            return verify_answer(decision["answer"], state)
        if decision["kind"] == "ask_human":
            return escalate(state, decision)
        tool = allowlisted_tool(tools, decision["tool"])
        args = validate_args(tool.schema, decision.get("args", {}))
        if tool.has_side_effects and not approval_granted(state, tool, args):
            return request_approval(tool, args)
        observation = tool.execute(args)
        state["history"].append({"decision": decision, "observation": observation})
        state["steps"] += 1
    return escalate(state, "step budget exceeded")
□ Define success and stop conditions
□ Add tool schemas and allowlists
□ Validate and authorize every call
□ Bound steps, tokens, cost, and latency
□ Persist trace and relevant state
□ Test happy path and adversarial path

15. Agent memory architectures

Short-term / workingCurrent conversation, plan, observations, and active context window.In-process state, checkpoint, graph state.“Step 3 completed; waiting for approval.”
Long-termInformation that persists across sessions.Database, object store, vector store.User preferences or organization policy.

Memory is not automatically truth. Store provenance, timestamp, source, confidence, sensitivity, retention policy, and an update/delete mechanism. Retrieval should be filtered by authorization.

16. Embeddings, chunking, similarity, and vector stores

An embedding maps an object such as text to a dense vector whose geometry encodes useful semantic relationships. A vector store indexes embeddings with metadata and returns nearest candidates for a query embedding.

Cosine similarity(a,b) = (a · b) / (||a|| ||b||)    |    Euclidean distance(a,b) = √Σᵢ(aᵢ − bᵢ)²
Pipeline stageExam explanation
IngestLoad files, normalize text, preserve metadata and access-control labels.
ChunkSplit into coherent units; use overlap or structure-aware boundaries to preserve context.
EmbedEncode chunks with an embedding model; store vectors plus source metadata.
IndexBuild an approximate nearest-neighbor index for efficient retrieval.
QueryEmbed the user query, apply metadata filters, retrieve top-k candidates.
Post-processDeduplicate, rerank, compress, and fit evidence to the model context.

Chunking trade-offs

Small chunks improve pinpoint retrieval but may lose context. Large chunks preserve context but dilute similarity and consume the context window. Structure-aware chunking follows headings, paragraphs, code blocks, tables, or semantic boundaries. Tune chunk size, overlap, top-k, and filters on a validation set rather than using universal values.

17. Retrieval-Augmented Generation (RAG) and agentic RAG

RAG combines a parametric language model with non-parametric external memory. Lewis et al. describe a dense vector index accessed by a neural retriever, allowing the generator to use retrieved evidence and improve specificity and factuality on knowledge-intensive tasks.[2]

Agentic RAG

In standard RAG, retrieval is often a fixed pipeline. In agentic RAG, an agent may decide whether retrieval is needed, transform the query, choose among knowledge sources, perform multiple searches, compare evidence, ask follow-up questions, and verify citations. The additional flexibility increases latency and failure modes, so use explicit budgets and evidence-based stop rules.

Retrieval improvements

TechniqueWhat it does
Query transformationRewrite, expand, decompose, or generate hypothetical answers to improve retrieval coverage.
Hybrid searchCombines dense semantic retrieval with sparse lexical retrieval such as keyword/BM25; useful for both meaning and exact terms.
Re-rankingUses a stronger cross-encoder or model to reorder initial candidates by query–passage relevance.
Context compressionExtracts only query-relevant spans, summaries, or claims from retrieved material.
Context engineeringDesigns what enters the context: order, provenance, delimiters, recency, permissions, token budget, and instructions.

18. Evaluation of retrieval and RAG performance

Evaluate the system in layers. A fluent final answer can hide a poor retriever, and a good retriever can be undermined by an unfaithful generator.

LayerMetric / questionInterpretation
Retrieval relevanceRecall@k, Precision@k, MRR, nDCGDid relevant evidence appear, and how highly was it ranked?
Context qualityContext precision, context recall, redundancy, coverageIs the supplied context relevant, sufficient, and non-repetitive?
Generation qualityAnswer correctness, completeness, relevanceDoes the response answer the question accurately?
FaithfulnessClaim entailment / citation supportAre claims supported by retrieved evidence rather than invented?
System qualityLatency, cost, tool success, abstention, escalation rateIs it practical, safe, and reliable in operation?
Recall@k = relevant items retrieved in top-k / all relevant items
Offline evaluation: Build a dataset of questions, gold evidence, expected answer attributes, and adversarial cases. Compare retrievers, chunking, k, rerankers, prompts, and models under fixed conditions.
Online evaluation: Monitor user feedback, correction rate, citation clicks, unresolved queries, latency, token use, tool failures, and safety incidents. Sample traces for human review.
Common RAG failure modes: bad chunking, missing documents, stale index, wrong permissions, query mismatch, retrieval noise, lost-in-the-middle context, citation mismatch, and confident answer despite insufficient evidence. A robust agent should abstain or ask for clarification when evidence is inadequate.

19. Engineering examination answer templates

Five-mark definition template

“An intelligent agent is a system that perceives an environment through inputs and selects actions to achieve objectives. In Agentic AI, the agent operates with a perception–reasoning–action loop, may use an LLM for interpretation and planning, accesses tools and memory, updates its state from observations, and terminates or escalates under explicit controls.”

Architecture-drawing template

Draw: user/environment → perception → state + memory → LLM/policy → planner/router → tool executor → observation → verifier → final response / next loop. Label arrows as observations, actions, and tool results. Add guardrails around tool execution and a stop condition.

Compare-and-contrast template

Define both systems, compare control flow, state, adaptability, observability, cost, and failure modes, then state one use case for each. End with a trade-off rather than claiming one approach is universally better.
